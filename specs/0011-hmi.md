# Spec 0011: HMI devices, tags, connections, alarms and screens

## Intent

Someone who has only a project's archive learns what its HMI devices show and do without TIA Portal: which HMI devices there are and of which WinCC family, which PLC each one talks to over which HMI connection, every HMI tag with the PLC tag or data block member it reads, every discrete and analog HMI alarm with its trigger and text, and every screen with its screen items and the HMI tags they show. It covers both WinCC families, Comfort/Advanced and Unified, as one model, since TIA stores their tags, connections and alarms alike. A coding agent gets it as text and JSON from `tiadump` and in the dump; a person sees it in the viewer. What is checked against TIA comes from a reference project TIA Portal V21 built, and what TIA's interface cannot build is marked as not checked.

## User scenarios

### Which HMI devices are there, and which PLCs do they talk to (P1)

- Given an archive with a Unified panel and a Comfort/Advanced runtime, when the HMI report is made, then each HMI device is listed with its name, its WinCC family and its device type.
- Given an HMI device with an HMI connection to a PLC, when the report is made, then the connection is listed with its name, the PLC it leads to, and its communication driver.
- Given an HMI device held only in a master copy, when the report is made, then it is not listed.
- Given an archive with no HMI device, when the report is made, then it says so and exits with 0.

### What does each HMI tag read (P1)

- Given an HMI tag linked to a PLC tag, when the report is made, then the tag is listed in its tag table with its name, data type, HMI connection, acquisition cycle and the PLC tag's name.
- Given an HMI tag linked to a member of a data block, when the report is made, then it gives the data block and the member's path, as `"Block".member`.
- Given an HMI tag with an absolute address and no link, when the report is made, then it gives the address and its HMI connection.
- Given an internal HMI tag, when the report is made, then it is listed as internal, with its data type.
- Given an HMI tag of a structured data type, when the report is made, then it gives the type and does not list the members.

### Which alarms does the HMI raise (P1)

- Given a discrete HMI alarm, when the report is made, then it is listed with its name, number, alarm class, trigger tag, trigger bit and event text.
- Given an analog HMI alarm, when the report is made, then it is listed with its name, number, alarm class, trigger tag, limit mode, limit value and event text.
- Given an alarm whose trigger tag is linked to a PLC tag, when the report is made, then the PLC tag can be found from the alarm through its trigger tag.

### What is on each screen (P2)

- Given a screen, when the report is made, then it is listed with its name, number, width and height.
- Given a screen with an I/O field bound to an HMI tag and a text, when the report is made, then each screen item is listed with its name, type, position and size, and the I/O field with the HMI tag it is bound to.

### Read it in the dump and in a program (P1)

- Given an archive with HMI devices, when it is dumped, then each HMI device gets a folder beside its PLCs with its connections, tag tables, alarms and screens as text files, and every block file is the same as before.
- Given any archive, when the report is asked for as JSON, then it holds the same facts as the text report.
- Given `--device` with an HMI device's name, when the report is made, then it holds only that device; with a name no device has, it exits with 1.

### See it in the viewer (P2)

- Given an archive with HMI devices, when it is opened, then the tree holds each HMI device with entries for its connections, tag tables, alarms and screens.
- Given a tag table, alarm list or screen is chosen, when it is shown, then the view lists what the report lists for it.
- Given an HMI tag linked to a PLC tag or data block member, when its PLC link is opened, then the viewer shows that tag in its tag table or that data block, and Back returns.

### It agrees with TIA (P1)

- Given the reference project `Hmi`, when the tests run, then every HMI device, connection, HMI tag, alarm, screen and screen item the reader reports agrees with what TIA Portal V21 gave for it through Openness when it built the project.
- Given a fact the reference project cannot hold because TIA's interface cannot build it, when it is reported, then the format page marks it as not checked against TIA.

### Nothing secret comes out (P1)

- Given an HMI device with runtime users and a stored password, when the report is made or the device is inspected, then no user's password and no password value appears.

## Requirements

- FR-001: `tiadump hmi <archive>` MUST write a report of every HMI device of the project itself, leaving out HMI devices held only in master copies or libraries.
- FR-002: The report MUST give each HMI device's name, WinCC family (Comfort/Advanced or Unified) and device type.
- FR-003: The report MUST list each HMI connection of a device with its name, the PLC it leads to, and its communication driver.
- FR-004: The report MUST list each tag table of a device with its HMI tags, each with name, data type, HMI connection or internal, and acquisition cycle.
- FR-005: For an HMI tag linked to a PLC tag, the report MUST give the PLC tag's name; for one linked to a data block member, the data block and the member's path; for one with an absolute address, the address.
- FR-006: When a data block member's path cannot be resolved, the report MUST give the data block and say that the member is not resolved, and MUST NOT fail.
- FR-007: The report MUST list each discrete HMI alarm with name, number, alarm class, trigger tag, trigger bit and event text, and each analog HMI alarm with name, number, alarm class, trigger tag, limit mode, limit value and event text.
- FR-008: The report MUST list each screen with name, number, width and height, and each of its screen items with name, type, position, size and the HMI tags it is bound to.
- FR-009: `tiadump hmi --json` MUST write the same report as JSON, and `tiadump hmi --device <name>` MUST limit it to that HMI device and exit with 1 if there is none.
- FR-010: `tiadump dump` MUST write, for each HMI device of the project, its connections, tag tables, alarms and screens as text files in a folder of the device beside the PLCs, and MUST write every block and PLC tag table file as before.
- FR-011: The viewer MUST show each HMI device of the project in the tree with entries for its connections, tag tables, alarms and screens, each showing what the report lists for it.
- FR-012: Opening an HMI tag's PLC link in the viewer MUST show the PLC tag in its tag table or the data block, as following a name in the source does.
- FR-013: A reference project `Hmi` MUST hold a PLC, a Unified HMI device and a Comfort/Advanced HMI device, built by TIA Portal V21 from invented sources, with HMI connections, internal HMI tags, HMI tags linked to PLC tags and to a data block member, HMI tags with absolute addresses, discrete and analog HMI alarms, and screens with an I/O field and a text (on the Comfort/Advanced device, an I/O field without a bound tag).
- FR-014: The library's tests MUST compare every HMI device, connection, HMI tag, alarm, screen and screen item of the reference project with what TIA gave for it through Openness when it built the project, and a difference MUST fail the tests.
- FR-015: `docs/FORMAT.md` MUST describe where the HMI objects are stored, and MUST mark as not checked against TIA what the reference project cannot hold: Comfort/Advanced alarms, Comfort/Advanced HMI tags linked to a PLC tag, and Comfort/Advanced screen items bound to an HMI tag.
- FR-016: The report, the dump, the viewer and `tiadump inspect` MUST NOT show a password or any value of an HMI runtime user, by the secret rule of spec 0004.
- FR-017: The HMI report MUST NOT count as source: it MUST NOT be searched as block source or change what the PLC's files hold.

## Success criteria

- SC-001: On the reference project and on each local sample with an HMI device, the report lists every HMI device, connection, HMI tag, alarm and screen the database holds, in under two seconds.
- SC-002: A person can tell from the report alone which PLC tags an HMI device reads, and which of them raise an alarm, without opening TIA Portal.
- SC-003: Every fact the reader reports about the reference project agrees with TIA, and no fact is presented as checked that TIA did not give.

## Out of scope

- Recipes, text and graphic lists, scripts, cycles beyond their name, logging, user administration and runtime settings: later specs.
- Screen items beyond name, type, position, size and bound HMI tags: their other properties, events, animations, faceplates, pop-ups and slide-ins, screen templates and the global screen.
- The members of an HMI tag of a structured data type.
- Controller alarms (Program_Alarm, ProDiag) and alarm texts kept in the PLC: the texts and alarms work.
- Non-integrated connections to other vendors' controllers, beyond listing their name and driver.
- The hardware of an HMI device: its interfaces, addresses and networks.
- WinCC Professional and other WinCC families.

None new. The reference project follows [ADR 0012](../docs/adr/0012-reference-projects-are-committed.md); the secret rule is spec 0004's.
