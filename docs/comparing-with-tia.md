# Comparing with TIA Portal

`tools/TiaOpennessExport` drives TIA Portal through Openness: it exports what TIA itself generates, so that `tiadump compare` can check the reader against it, and it builds the reference projects. The result of the last comparison is in section 17 of [the format](FORMAT.md); what is still open is under its Open questions.

## Setup

This needs Windows, TIA Portal V21, and a user in the group `Siemens TIA Openness`, signed in again after joining it. TIA may ask to confirm the first access.

```bash
dotnet build tools/TiaOpennessExport -c Release
```

The project references TIA's Openness assemblies under `C:\Program Files\Siemens\Automation\Portal V21\PublicAPI\V21\net48`; set `TiaPublicApi` when TIA is installed elsewhere. It is not in `TiaTools.slnx`, so the solution still builds without TIA.

## Comparing an archive

The exporter retrieves a copy of the archive into an empty folder, writes generated source and SimaticML per block, and closes the copy unsaved. It never compiles or saves, and it skips protected blocks. Keep the folder's path short: TIA refuses a long one and says only "Unable to retrieve the project". Keep both output folders outside this repository, like every archive.

```bash
tools/TiaOpennessExport/bin/Release/net48/TiaOpennessExport.exe archive Project.zap21 C:/Users/me/tc <export folder>
```

```bash
tiadump dump Project.zap21 <dump folder>
```

```bash
tiadump compare <dump folder> <export folder>
```

TIA exports SimaticML only for a compiled block. An archive that was never compiled after an upgrade still gives all its source, and `manifest.tsv` says which exports it refused. To get more XML, compile the retrieved copy:

```bash
tools/TiaOpennessExport/bin/Release/net48/TiaOpennessExport.exe compiled-copy C:/Users/me/tc/Project/Project.ap21 <export folder>
```

This compiles each block that is not fail-safe, exports, and closes unsaved. Only point it at a retrieved copy. Fail-safe blocks need the safety program's password, so to include them, open the copy in TIA yourself, log in to the safety program, compile, and leave it open. Then run `TiaOpennessExport attach <export folder>`, which exports from the open TIA. Close the copy unsaved afterwards.

## Reference projects

A reference project ([spec 0008](../specs/0008-reference-projects.md)) is an invented program that TIA Portal builds, kept in `tests/reference/<name>/` with the archive TIA built and the source it generated, so the library's tests compare the reader with TIA in every run, on any machine ([ADR 0012](adr/0012-reference-projects-are-committed.md)). `FillingLine` is the demo project.

- `sources/`: one folder per PLC, named as the PLC, with `order.txt`, the order in which TIA has to generate the files (what a source names must exist first), and `PLC data types/`, `Program blocks/` and `PLC tags/`. The folders below the first two become the project's folders. A tag table is a `.tsv` of name, data type, address and comment. `protect.txt` names blocks to protect with know-how protection, under a password written in the exporter: it guards nothing invented. Write sources with text outside ASCII as UTF-8 with a byte order mark; TIA reads a source without one in the system's code page. TIA refuses some ordinary words as names, among them `name` in a UDT and `timer` and `NAME` in an FB; the build names each such row.
- Blocks TIA takes no text source for, LAD, FBD and GRAPH, are `.xml` files in SimaticML, listed in `order.txt` like the others and imported into the folder they are in ([spec 0009](../specs/0009-logic-languages.md)). V21's import wants more than its schemas in `PublicAPI/V21/Schemas` say: `<Namespace />` among a block's attributes, and none of `MemoryLayout` on a GRAPH block; in a LAD network the parts of each rung in the order the current flows, a parallel branch closed by an `O` part, an unused output such as a timer's `ET` wired to an `OpenCon`, and in FBD an unwired `en` wired to one; a jump's label wired to its pin `label`; UIds on every `Symbol`, `Component` and `Blank` of an SCL network, and none at all in an STL network. In GRAPH, a network inside `Graph` takes no namespace of its own; an action is its text as tokens, `<Token Text="#valve" />`, with `Event`, `Qualifier` and `Interlock` all written, and every line but the last ends in a line feed inside the token's text; a step must not share a name with a member, since each step becomes one; the interface needs the input `ACK_EF`; and a call in an action is `CALL "Tick"()`, a block without parameters. TIA's import errors name most of this; where one only says `Import failed`, import smaller variants of the block side by side to find the part it refuses. A step or transition must not share its name with a member in any letter case, or the import says only that.
- `sources/hardware.tsv`, when a project is about its hardware ([spec 0010](../specs/0010-hardware.md)): one tab-separated row per thing TIA is to build, in the order given. `subnet` name, kind (`Ethernet`, `Profibus`); `device` name, order number, firmware (empty for the newest the catalog has), device group path (`Line/Cell`); `module` device, slot, order number, firmware, name, then start addresses such as `I=10`; `interface` device, interface name, subnet, then IP address, subnet mask and PROFINET device name or `auto`, or for PROFIBUS the address alone; `ipelsewhere` device, interface, to have the IP address set at the device, which TIA allows only on an IO controller's interface; `iosystem` device, interface, name, number; `iodevice` device, interface, IO system. With it the devices come from this file, and each PLC folder names a CPU it creates. A DP interface module's interface is the module itself, named as the device. `TiaOpennessExport catalog <text>...` lists the catalog entries that match, to find an order number.
- `Watch and force tables/`: watch tables and a force table as SimaticML, in the form TIA exports them, imported after the program is compiled, a subfolder as a table group ([spec 0015](../specs/0015-tables-and-cross-references.md)). No schema is published; the build prints TIA's export of an empty table with one comment line first. V21's import refuses `ModifyIntention` and `ForceIntention` as read-only, so no reference entry has its value selected, and a force table replaces the PLC's own.
- `safety.tsv` in a PLC folder, for a safety program ([spec 0012](../specs/0012-safety.md)): rows `group`, name, main safety F-FB and the name of its instance DB, which replace TIA's default F-runtime group; and rows `set`, an object (`group:<name>`, `settings`, `blocknumbers`, `cpu`, or `item:<device>/<item>` for an F-I/O's submodule), an Openness attribute and its value, for what TIA's defaults would hide. They are applied before the PLC is compiled; a row TIA refuses counts as a refused source. F-blocks are SimaticML like LAD and FBD, with `F_FBD`, `F_LAD` and `F_DB` as their language; an F-FB's instance DB is made by the build. Without a password TIA compiles the safety program through Openness; one F-DQ cannot be written from two F-runtime groups.
- `password.txt` in a PLC folder: after compiling, the build sets the safety password written in the exporter, invented like the know-how one, and never logs in with it. Setting it counts as a change, so that PLC's collective F-signature is then none.
- `cpu.txt`, in a PLC's folder when needed: the order number of its CPU, which the build takes in the catalog's latest version; without it the PLC gets a CPU 1516-3 PN/DP. `MoreLanguages` uses `6ES7 315-2EH14-0AB0`, an S7-300 ([spec 0016](../specs/0016-remaining-languages.md)): a classic CPU's blocks have standard access only, so their SimaticML must not name a `MemoryLayout`. `TechnologyObjects` uses a CPU 1517T-3 PN/DP, whose firmware V3.1 takes the newest versions of the motion objects, and a CPU 1511C-1 PN for its counter channels.
- Technology objects ([spec 0013](../specs/0013-technology-objects.md)) are `.to` files in `Technology objects/` and the folders below it, listed in `order.txt` before any block that names them: a line `type` (`TO_PositioningAxis`), a line `version` (`8.0`), then one `parameter<TAB>value` per parameter to set, by the name Openness gives it. A value `@HSC_1` is the CPU's device item of that name, which a counter's `Configuration.Module` takes. Openness refuses some parameters as read-only, such as a PID controller's `Retain.CtrlParams` and `Config.CoolFactor`, and the build names each it refuses. It cannot create measuring inputs, output cams or cam tracks, nor import them. An axis needs no drive when it is virtual, `VirtualAxis.Mode` 1.
- `accept.tsv`, in a PLC's folder when needed: a technology object's name and a compile error TIA gives for it, one per line, which the build accepts. Only for a missing hardware connection, which spec 0013 leaves out: TIA compiles no external encoder without its telegram, and no SSI encoder without hardware. Such an object is archived without a compiled image, so its defaults are not in the archive.
- A ProDiag function block has no source form: a `.prodiag` file in `order.txt` holds its number and its instance data block's, and the build creates both, empty, through Openness; TIA adds the OB that calls it. A member of a PLC data type in a global data block takes `<AssignedProDiagFB>` in SimaticML, and so does an instance data block among its attributes, without a `MemoryLayout`, which is fixed for one. A data block with an assigned ProDiag function block is exported as SimaticML beside its generated source. TIA exports nothing of a ProDiag block itself.
- TIA Portal V21 refuses SimaticML with `<Supervisions>` on a function block or PLC data type, whatever its `<Namespace>`, in a software unit or not, and with or without its import option to ignore unit attributes: "The namespace '' is incorrect". Openness has no other way to create them, so no reference project holds one.
- In STL, `pointer`, `block` and `at` are reserved and cannot name a variable, and `TAR1` and `TAR2` write only to a double word in memory or a data block. An absolute address in an STL source, such as `%MD24` or `%T1`, gets a tag of TIA's own, `Tag__` and a number, in the default tag table.
- An HMI device is a folder with a `device.txt` ([spec 0011](../specs/0011-hmi.md)): tab-separated `family` (`Unified` or `Advanced`), `type` (a catalog type identifier) and `plc`, the PLC it connects to; HMI devices are built after the PLCs. A `Unified` device is built through TIA's HmiUnified API from `tags.tsv` (table, name, PLC tag or `"DB".member` without quotes, data type for an internal tag), `alarms.tsv` (kind, name, trigger tag, bit or limit mode, limit, class, text) and `screens.tsv` (screen, number, item, type `IOField`, `Text` or `Button`, left, top, width, height, bound tag or text), each with a header row. An `Advanced` device is an ET 200SP Open Controller with WinCC RT Advanced (`device` names the station): its software PLC is built from the PLC folder `plc` names inside it, and its SimaticML tag tables in `HMI tags/` and screens in `Screens/` are imported, with `@Connection@` standing for the HMI connection TIA names. Each device gets an integrated HMI connection to its PLC through the hardware API. The build writes `generated/<HMI device>/`: for Unified, `device.tsv`, `connections.tsv`, `tags.tsv`, `alarms.tsv` and `screens.tsv` read back from the API; for Comfort/Advanced, `device.tsv`, `connections.tsv` and TIA's SimaticML export of each tag table and screen.
- What TIA V21 allows for HMI: the trial refuses Comfort and Basic panels (no WinCC Comfort licence), and Unified needs its trial licence activated once in TIA's window, by adding a Unified device by hand. Openness creates no Comfort/Advanced alarm, link from an HMI tag to a PLC tag, or tag binding of a screen item, and no recipe in either family. An HMI import TIA refuses while it creates an object, such as one naming a connection that does not exist, can end the Openness session, so the build saves before each one.
- `<name>.zap21`: the archive TIA built.
- `generated/safety/<PLC>.tsv`, for each PLC with a safety program: what TIA reports about it through Openness, one value per row as kind, name, attribute and value, which the tests compare with `tiadump safety`.
- `generated/`: TIA's generated source of each block, its SimaticML export of each block it generates no source for, and its export of each tag table, watch table and force table, with `manifest.tsv`, as an export for a comparison holds. Per PLC, `xref.tsv` is TIA's cross-reference list from Openness's `CrossReferenceService`, one row per location, asked for every block, PLC data type and tag; a tag table, a watch table and a force table offer no such service. `hardware.tsv` holds what TIA reports through Openness about the hardware: every readable attribute of each device, device item, I/O address, interface node, subnet and IO system, as rows of kind, path, attribute and value, but none named like a password, key or certificate, nor the author's name or the build's time. For each technology object, `TO.<name>.tsv`: every parameter Openness reports, with its .NET type and value; its manifest row has kind `TO`, its own kind as the language and its version as the note. To export SimaticML TIA needs the blocks compiled, so the build compiles each PLC, and a compile error counts as a refused source.
- `known.tsv`, when needed: `plc`, `kind`, `name`, `reason` for a block whose dump differs from TIA's, or that has no generated source; with kind `xref`, a cross-reference row that differs, `ours: ` or `TIA's: ` and the row as the test prints it. A listed block or row that matches again fails the tests, so the list stays true. With kind `TO`, a technology object TIA did not compile, whose parameters without a stored value are then not compared, or `object/parameter` for a value Openness gives in other units than the data block holds.
- Texts in several project languages ([spec 0014](../specs/0014-texts-and-alarms.md)): `sources/languages.txt` sets the project languages, a line `editing de-DE`, `reference en-US` or `active fr-FR` each. In a tag table, the comment can then be fields of the form `de-DE=text`, one per language. `block texts.tsv` beside `order.txt` sets a block's `Title` or `Comment` per language, as block name, field, then `culture=text` fields; network titles and comments and member comments in several languages need a block in SimaticML, which takes one `MultiLanguageText` per language. `PLC text lists/<name>.tsv` is a PLC text list: a line `ListRange` with `Decimal`, `Binary` or `Bit`, a line `Comment`, then one line per entry with from, to and `culture=text` fields. `PLC alarms/alarms.tsv` holds the instance texts of program alarms, with a header row: `Location` (the instance DB), `Alarm name` (the member), `Alarm class`, and columns such as `Alarm text de-DE`, `Info text en-US` or `Additional text 1 fr-FR`; an empty cell keeps the alarm type's value. Openness takes text lists and alarm texts only as xlsx and cannot set an alarm type's texts, so the build writes these files in the layouts of TIA's own export and imports them after the first compile, then compiles again.
- `generated/`: TIA's generated source of each block, its SimaticML export of each block it generates no source for, and its export of each tag table, with `manifest.tsv`, as an export for a comparison holds. A project with `languages.txt` also has SimaticML of every block, because only SimaticML lists every language's text, and `languages.txt`, `alarmclasses.dat`, and per PLC `textlists.xlsx` and `alarms.xlsx`, TIA's exports of its languages, alarm classes, text lists and alarm instance texts. To export SimaticML TIA needs the blocks compiled, so the build compiles each PLC, and a compile error counts as a refused source.

After changing a reference project's sources, build it again; this needs the setup above, and the work folder's path short:

```bash
tools/TiaOpennessExport/bin/Release/net48/TiaOpennessExport.exe reference C:/Users/me/tr tests/reference/<name>
```

It takes several folders at once, and builds them all in one TIA session. With `TIA_STALE_EXPERIMENT` set to `<project>|<source file>|<folder outside the repository>|<block folder>`, the build of that project also replaces one block from the source file without compiling and archives the project twice into that folder, before and after compiling it: what showed that TIA keeps its cross-reference list current and names it in the database ([the format](FORMAT.md), section 21). For each it creates a new project from the sources, archives it and exports its generated source, and replaces the committed files only when TIA took every source; otherwise it names each refused source with TIA's error and changes nothing. It opens no other project, and deletes the work folder when it is done. Each build adds a new archive to the history, so build a project again only when its sources changed.

To take the README's pictures again, after a change to how the viewer looks:

```bash
dotnet run --project tools/ReadmePictures -c Release -- tests/reference/FillingLine/FillingLine.zap21 .github/images
```

It renders the viewer without a screen, at the same size every time, so only what changed in the viewer changes in the pictures. Run it on Windows: text is drawn with the machine's fonts, and the current pictures were taken there.
